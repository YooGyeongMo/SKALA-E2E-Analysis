# 팀 회고 종합 보고서

docs/opinions/ 4인(유경모, 안소유, 박서영, 승민)의 회고를 주제별로 통합하고
중복을 제거한 문서다. 각 제안에는 제안자와 함께 데이터 분석/ML 엔지니어링/
파이썬 코드 품질 세 관점의 타당성 평가를 붙였고, 회고 속 수치는 실측
보고서(output/report.md, docs/reports/report-v1.md)와 대조해 팩트체크했다.

## 1. 전원 합의 (4/4): 이번 프로젝트의 핵심 교훈

네 명이 서로 다른 표현으로 같은 지점을 짚었다. 팀의 공식 결론으로 삼는다.

| 합의 내용 | 요지 |
|---|---|
| 평균만 보면 틀린다 | 평균은 39.35 vs 45.71시간으로 다르지만 중앙값은 두 그룹 모두 40시간. 정확한 해석은 "고소득 그룹은 초과근무자(꼬리) 비중이 높다"이며, 평균 차이는 분포의 꼬리에서 온다 |
| 대표본에서 p만 보면 틀린다 | n이 3만이면 미미한 차이도 p < 0.001이 된다. p(차이의 실재)와 Cohen's d(차이의 크기)는 별개의 질문이므로 반드시 병행한다 |
| 모듈 분리 + config 단일 관리가 협업을 만들었다 | 6단계 모듈 분리 덕에 병렬 작업에서 충돌이 없었고, config.yaml 단일 출처 덕에 분석 조건이 전원 동일했다 |
| 사실과 해석의 분리 | 수치는 자동 생성 보고서(report.md)가, 해석과 회고는 opinions/가 담당한다. 보고서와 코드가 어긋날 수 없는 구조가 신뢰성을 만들었다 |

## 2. 다수 합의 (3인 이상): 개선 로드맵 통합 우선순위

네 명의 개선 의견에서 중복을 제거하고 제안 인원 순으로 정렬했다.

| 순위 | 개선 항목 | 제안 | 타당성 평가 |
|---|---|---|---|
| 1 | 초과근무 비율(hours > 40) 이진화 + 카이제곱 검정 | 유경모, 안소유, 승민 | 채택 권고. 핵심 결론 문장("비중이 높다")을 아직 평균 검정으로만 지지하고 있어 방법론적 불일치가 실재한다. "평균 검정 > 중앙값 발견 > 해석 수정 > 수정된 해석의 재검정"으로 논증이 닫힌다. 구현도 scipy chi2_contingency로 가벼움 |
| 2 | 교차검증(Stratified 5-Fold) | 유경모, 안소유, 승민 | 채택 권고. 단일 8:2 분할의 운을 제거하고 성능의 표준편차까지 보고. 클래스 불균형(76:24)이므로 Stratified가 필수 조건이라는 승민 의견이 정확하다 |
| 3 | 오즈비/피처 중요도 해석 | 유경모, 안소유, 승민 | 채택 권고. "수치 상관은 약한데(최대 0.15) 정확도는 84.6%"의 이유(신호는 범주 변수에 있다)를 모델이 배운 내용으로 증명하는 단계. 안소유의 "단변량 유의가 다변량 중요를 보장하지 않는다"는 지적이 이 작업의 해석 프레임이 된다 |
| 4 | 외부 검증(adult.test 16,281행) | 유경모, 승민 | 채택 권고. 같은 파일을 쪼갠 내부 평가보다 정직한 일반화 성능. 라벨 끝 마침표(">50K.") 함정 처리가 전처리 강건성의 증거가 된다 |
| 5 | 평균 차이의 95% 신뢰구간 병기 | 유경모, 승민 | 채택 권고. p 중심 보고에서 구간 중심 보고로. 효과의 크기와 불확실성을 한 번에 전달 |
| 6 | 교란변수 통제(연령/교육 통제 로지스틱 회귀) | 유경모, 승민 | 조건부 채택. 방향은 옳으나 statsmodels 의존성 추가가 필요하므로 1~5 완료 후 별도 이슈로 |

## 3. 고유 관점: 한 사람만 잡아낸 날카로운 지적

중복 제거 과정에서 오히려 돋보인, 각자만의 기여다.

### 박서영 (검정 절차의 이론적 엄밀성)
- 보조가설(age)에는 사전 시각화가 없다: 주가설은 "시각화 확인 후 검정" 절차를
  따랐는데 보조가설은 검정만 있다. 절차 일관성을 위해 age 분포 차트 추가 제안
- 다중비교 미보정: 주가설과 보조가설을 같은 유의수준으로 각각 검정하면 1종 오류가
  누적된다. 보조가설이 탐색적 보강임을 명시하거나 Bonferroni 보정 필요
- 방어 코드: income 그룹이 3개 이상이 되면 현재 코드는 조용히 세 번째 그룹을
  무시한다. assert 한 줄로 잡을 수 있는 실전형 지적
- Q-Q 플롯: "40시간 봉우리 = 비정규"라는 판단의 시각적 근거 보강

평가: 세 지적 모두 타당하다. 특히 다중비교와 그룹 수 방어는 코드 리뷰에서
놓치기 쉬운 통계 이론과 방어적 프로그래밍의 교차 지점이다.

### 안소유 (해석의 정확성과 코드 위생)
- Welch t와 Mann-Whitney U는 같은 가설의 반복 검정이 아니다: 전자는 평균,
  후자는 순위/분포를 검정하므로 "교차검증"이라 부르되 각각의 역할을 구분해
  서술해야 한다. 보고서 문구 수정에 직결되는 지적
- 정제 전후 분포 보존 확인: 결측 행 제거(7.4%)가 income 비율이나 근로시간
  분포 자체를 바꿨는지 전후 비교로 검증해야 한다. 결측이 특정 범주 컬럼에
  몰려 있었으므로 특히 유효한 우려
- 주석에 실행 결과값을 하드코딩하지 말 것: 코드 머리말의 수치(39.35 등)는
  분석 조건이 바뀌면 실제 결과와 어긋난다. 주석은 설계 의도만, 수치는
  자동 보고서만 담당하도록 분리

평가: 세 번째 지적은 현재 코드베이스에 실제로 존재하는 문제다(stats.py 등의
머리말에 실측치가 적혀 있음). 다음 코드 수정 시 반영을 권고한다.

### 승민 (ML 튜닝과 운영 확장)
- F1 0.66의 원인 진단: recall 0.60이 병목이므로 class_weight="balanced"와
  분류 임계값 튜닝으로 precision-recall 트레이드오프를 능동 제어하자는 제안.
  "성능이 낮다"가 아니라 "어느 방향으로 틀릴지 선택한다"는 프레임이 정확하다
- GitHub Actions cron으로 무인 자동화: 로컬 schedule 데모를 넘어 CI가 매일
  파이프라인을 돌리고 report.md를 자동 커밋하는 운영 수준 제안
- Streamlit 대시보드: config 매개변수를 웹에서 동적 제어하는 제품화 방향

### 유경모 (검증 문화)
- 제공된 코드를 그대로 쓰지 않고 검증: na_values 함정(결측 4,262셀)과
  Polars 빈 줄 함정을 실측으로 발견
- 검증값을 로그로 출력하는 설계: 계산만 하고 숨겼다면 빈 줄 버그는 영영
  몰랐을 것. 파이프라인에 자기 검증 지표를 심는 문화의 근거

## 4. 검증 노트 (회고 수치 팩트체크)

회고 문서들의 수치를 실측 보고서와 대조한 결과다. 공유 전에 명확히 해 둔다.

| 회고 속 수치 | 판정 |
|---|---|
| 평균 39.35 / 45.71, 차이 6.36시간, d 0.545, 중앙값 40/40 | 실측 일치 (report.md) |
| F1 0.66, recall 0.60, 불균형 76:24 | 실측 일치 (classification_report) |
| 초과근무 비율 "저소득 약 25% vs 고소득 약 45%" | 미실측 추정치. 비율 검정(로드맵 1번)을 실행해야 확정된다. 공유 시 "예상"으로 표기할 것 |
| 95% 신뢰구간 "[6.1, 6.6]시간" | 미실측 추정치. CI 산출(로드맵 5번) 전이므로 확정 수치처럼 인용하지 말 것 |

## 5. 실행 계획 제안 (이슈 후보)

로드맵을 실제 이슈로 전환할 때의 묶음 제안이다.

1. 통계 심화 이슈: 비율 검정 + 신뢰구간 + 다중비교 각주 + 그룹 수 assert
   (stats.py 한 파일, 박서영/안소유/승민 제안 통합)
2. 시각화 보강 이슈: age 분포 차트 + Q-Q 플롯 + 표본수 막대 (visualize.py)
3. ML 확장 이슈: Stratified 5-Fold + adult.test 외부 검증 + 오즈비 표
   + class_weight 실험 (model.py, config.yaml)
4. 코드 위생 이슈: 머리말 주석의 실측치를 설계 의도 서술로 교체 (전 모듈)
5. 운영 확장 이슈(후순위): GitHub Actions cron, Streamlit

## 6. 결론

네 명의 회고는 표현은 달랐지만 같은 곳을 향했다: "숫자가 나왔다"와 "결론이
맞다" 사이에는 검증이라는 거리가 있고, 그 거리를 좁히는 것(중앙값 확인,
효과크기 병행, 교차 검정, 함정 실측, 전후 비교)이 이번 프로젝트에서 팀이
실제로 연습한 것이다. 위 로드맵 1~5는 그 연습을 코드로 완성하는 다음 단계다.
