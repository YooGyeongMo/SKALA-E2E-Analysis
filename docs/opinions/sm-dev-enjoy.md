# sm-dev-enjoy 의견/회고

## 개별 의견 (내가 맡은 파트의 기술적 판단)

팀원의 교차 검증 피드백 및 검증 결과를 바탕으로, 본 프로젝트의 분석 방법론과 머신러닝 파이프라인, 그리고 엔지니어링 측면에서의 기술적 판단과 고도화 방향을 다음과 같이 정리하고 평가했습니다.

### 1. 방법론적 완결성 확보 (Tier 1: 분석 논증 사이클의 완성)
* **초과근무 비율(hours > 40) 이진화 및 비율 검정(Chi-Square / Proportions Z-Test)**
  * **기술적 맥락**: 본 프로젝트의 핵심 결론은 "고소득층이 일률적으로 더 오래 일한다"가 아니라 "고소득 그룹은 중앙값(40시간)은 동일하나, 주 40시간 초과 근무자 비중이 높다"라는 것입니다.
  * **기술적 판단**: 정작 가설 검정은 '평균(Mean)'에 대한 Welch t-test만 수행되었기에, 결론 문장과의 방법론적 불일치가 존재합니다. 따라서 `hours-per-week > 40` 변수를 이진화(Binary)하여 저소득층(~25%)과 고소득층(~45%) 간의 초과근무 비율 차이에 대해 **카이제곱 검정(Chi-Square Test)** 또는 **비율 Z-검정(Proportions Z-Test)**을 추가 수행해야 합니다.
  * **의의**: `평균 검정 -> 중앙값 동일성 발견 -> 해석 수정 -> 수정된 해석(비율 차이)의 재검정`이라는 완결된 논증 구조를 완성할 수 있습니다.
* **다변량 분석을 통한 교란변수(Confounder) 통제 (Multivariate Logistic Regression)**
  * **기술적 맥락**: 단변량 t-test는 근로시간 하나만 비교하므로, 연령(`age`)이나 교육수준(`education-num`) 같은 교란변수의 영향이 통제되지 않습니다.
  * **기술적 판단**: `statsmodels`의 로지스틱 회귀를 활용하여 연령과 교육수준을 통제 변수로 지정한 후, `hours-per-week` 1시간 증가에 따른 소득 $50K 초과 **오즈비(Odds Ratio)** 및 **95% 신뢰구간(CI)**을 산출해야 합니다. 이를 통해 타 변수의 영향을 배제한 '순수 근로시간의 효과'를 엄밀하게 분리할 수 있습니다.
* **95% 신뢰구간(Confidence Interval) 중심 보고**
  * p-value는 대용량 표본($n=32,561$)에서 지나치게 작아지는 한계가 있으므로, 평균 차이($6.36$시간)의 **95% 신뢰구간([6.1시간, 6.6시간])**을 함께 보고함으로써 효과의 크기와 불확실성을 동시에 전달하는 현대 통계학 표준을 지향해야 합니다.

### 2. 머신러닝 파이프라인의 정직성과 해석력 (Tier 2: ML 모델링 고도화)
* **외부 홀드아웃 세트(`adult.test` 16,281행) 독립 평가**
  * 단순 단일 파일 내 8:2 Train/Test Split에 그치지 않고, UCI 공식 홀드아웃 데이터인 `adult.test` 데이터를 최종 평가에 주입해야 합니다. 특히 `adult.test` 라벨 끝의 마침표(`>50K.`) 정제 전처리 함정을 파이프라인(`src/e2e/clean.py`)에서 다룸으로써 전처리 파이프라인의 강건함과 진정한 일반화 성능을 정직하게 검증할 수 있습니다.
* **Stratified 5-Fold 교차검증 & 임계값(Threshold) / Class Weight 튜닝**
  * 클래스 불균형(76:24) 환경에서 단일 Split의 운에 따른 평가를 방지하기 위해 **5-Fold Stratified Cross-Validation**을 적용해야 합니다.
  * 현재 Logistic Regression의 F1-score(약 0.66) 한계는 Recall(0.60)이 다소 낮기 때문입니다. `class_weight="balanced"` 설정 및 Classification Decision Threshold 튜닝을 통해 Precision-Recall Trade-off를 능동적으로 제어하는 모델링 서사를 구축하는 것이 적절합니다.
* **모델 계수(Coefficient) 기반 피처 중요도 및 오즈비 변환**
  * Logistic Regression 파이프라인 학습 후 범주형/수치형 피처의 계수를 오즈비로 변환하거나 **Permutation Importance**를 산출하여, EDA 상관관계 분석에서 수립한 가설("소득 예측의 핵심 신호는 특정 범주형 변수와 근로시간의 상호작용에 있다")을 ML 모델 파라미터 관점에서 직관적으로 증명할 수 있습니다.

### 3. 엔지니어링 및 파이프라인 운영 확장 (Tier 3: MLOps 및 제품화)
* **GitHub Actions 기반 무인 파이프라인 자동화**: 현재 로컬 `schedule` 모듈 실행 수준을 넘어, GitHub Actions Cron Workflow를 구축하여 매일/매주 단위로 파이프라인 실행, 테스트 통과, `report.md` 자동 커밋 및 PR 생성을 무인화할 수 있습니다.
* **Streamlit 대시보드 구축**: 단순 마크다운 보고서 생성을 넘어 `config.yaml` 매개변수와 분석 가설을 동적으로 제어하는 웹 인터랙티브 대시보드로 확장할 가치가 있습니다.

## 팀 의견 (협업 방식 회고)

* **모듈화 아키텍처와 Pydantic Config 단일 출처 관리의 이점**: `config.py`로 모든 하이퍼파라미터와 가설 변수를 단일 통제하고, `clean.py`, `stats.py`, `model.py`, `report.py`로 역할을 명확히 분리함으로써 팀원들이 각자 파트를 독립적으로 개발하고 머지하는 데 충돌이 전혀 없었습니다.
* **객관적 결과(보고서)와 주관적 해석(Opinions)의 분리**: Jinja2 템플릿 기반 수치 자동 생성 파이프라인(`report.md`)과 엔지니어 각자의 해석 및 회고를 담는 `docs/opinions/` 디렉토리를 분리한 설계는 데이터 분석 프로젝트의 객관성과 재현성을 담보하는 뛰어난 협업 방식이었습니다.
* **Git Flow 및 CI 품질 게이트의 안정성**: Issue 발행 -> 기능 브랜치 작성 -> PR 생성 -> pytest/pre-commit CI 검증 -> 코드 리뷰 -> Main 머지 흐름을 준수하여 메인 브랜치의 신뢰성을 100% 유지할 수 있었습니다.

## 배운 점

* **통계적 유의성($p$-value)과 실제 효과 크기(Effect Size)의 명확한 구별**: 대용량 데이터셋에서는 아주 미세한 평균 차이도 $p < 0.001$로 기각되므로, Cohen's d 및 95% 신뢰구간을 통해 실질적인 차이의 크기를 반드시 병행 검증해야 함을 명확히 배웠습니다.
* **대표값(Mean vs Median)과 분포 꼬리(Tail) 해석의 중요성**: 두 집단 모두 중앙값이 40시간이라는 점을 무시하고 평균만 보고 "고소득층이 더 일한다"고 결론 내리는 오류를 방지하고, 초과근로자 비중(꼬리 분포)이라는 본질적 요인을 탐색하는 시각의 중요성을 터득했습니다.
* **단변량 통계 검정과 다변량 ML 피처 중요도의 격차**: t-test상 유의미한 변수가 다변량 모델링(Logistic Regression, Random Forest)에서도 반드시 높은 중요도를 갖는 것은 아니며, 타 변수와의 상관관계 및 교란효과를 함께 고려해야 함을 이해했습니다.
