# 판교 8반 P259 안소유 의견/회고

## 개별 의견 (내가 맡은 파트의 기술적 판단)

* 전체 분석 결과와 코드를 검토하면서, 단순히 통계적으로 유의하다는 결론보다 **분포의 형태와 해석의 정확성**을 함께 보는 것이 중요하다고 판단했다.
* 소득 그룹별 주당 근로시간은 평균이 `39.35시간`과 `45.71시간`으로 약 `6.36시간` 차이가 있었지만, 중앙값은 두 그룹 모두 `40시간`으로 동일했다. 따라서 단순히 "고소득자가 더 오래 일한다"고 표현하기보다는, **고소득 그룹에서 장시간 근로 관측치가 상대적으로 더 많이 나타나는 분포 특성이 평균 차이에 영향을 준다**고 해석하는 것이 더 적절하다고 보았다.
* 현재 보고서의 "고소득 그룹은 초과근무자 비중이 높다"는 해석을 보다 직접적으로 뒷받침하려면, `hours-per-week > 40`을 분석상의 기준으로 정의하여 그룹별 40시간 초과 근로 비율을 추가로 산출하는 것이 좋다고 판단했다.
* 통계 검정에서는 Welch t-test와 Mann-Whitney U를 함께 사용한 점은 결과를 여러 관점에서 확인한다는 측면에서 의미가 있었다. 다만 Welch t-test는 **평균 차이**, Mann-Whitney U는 **순위 및 분포 차이**를 검정하므로 동일한 가설을 반복 검정하는 것으로 해석하지 않고 각각의 역할을 구분하는 것이 더 정확하다고 생각했다.
* 표본이 약 3만 건으로 크기 때문에 p-value만으로 차이의 중요도를 판단하지 않고 Cohen's d를 함께 사용한 점은 적절하다고 판단했다. 통계적 유의성과 실제 차이의 크기를 별도로 해석하는 것이 필요하다는 점을 확인했다.
* 머신러닝에서는 `hours-per-week`의 t-test 결과가 유의하다는 사실만으로 해당 변수가 모델에서 반드시 중요한 변수라고 단정할 수 없다고 보았다. 통계 검정은 단변량 관계를 보는 반면 실제 모델은 나이, 교육수준, 직업 등 여러 변수를 동시에 사용하므로, 두 결과는 구분하여 해석하는 것이 적절하다.

## 팀 의견 (협업 방식 회고)

* 데이터 수집, 정제, 통계 분석, 시각화, 머신러닝, 보고서 생성을 각각 모듈로 분리하여 작업한 구조가 협업에 효과적이었다. 특정 단계의 코드를 수정하더라도 다른 분석 단계에 미치는 영향을 줄일 수 있었다.
* `config.yaml`을 통한 설정 관리와 자동 보고서 생성 방식 덕분에 분석 조건과 결과를 팀원 간 동일하게 공유하기 쉬웠다.
* 분석 결과를 단순히 수치만 공유하는 것이 아니라, 평균과 중앙값이 왜 다른지, p-value와 효과크기를 어떻게 구분해서 해석해야 하는지 등을 함께 논의하면서 결과에 대한 설명이 더 정교해졌다.
* Git 기반으로 작업 내용을 분리하여 관리하면 누가 어떤 분석을 추가하거나 수정했는지를 추적하기 쉽고, 결과 변경에 대한 원인을 확인하는 데도 도움이 된다고 느꼈다.
* 한편 여러 팀원이 서로 다른 분석 결과나 해석 문장을 추가할 경우 코드, 주석, 보고서의 내용이 서로 달라질 수 있으므로 **최종 분석 결과와 표현을 한 번 더 함께 검토하는 과정**이 중요하다고 생각했다.

## 배운 점

* 평균만으로 데이터의 대표적인 특성을 판단하면 실제 분포를 잘못 해석할 수 있다는 점을 확인했다. 이번 데이터처럼 두 그룹의 중앙값이 모두 40시간인데 평균은 크게 다른 경우, 평균 차이가 어디에서 발생했는지 분포와 함께 확인해야 한다.
* `p < 0.001`과 같은 매우 작은 p-value가 반드시 큰 효과를 의미하는 것은 아니며, 특히 대표본에서는 작은 차이도 쉽게 통계적으로 유의하게 나타날 수 있다는 점을 배웠다. 따라서 Cohen's d와 같은 효과크기를 함께 확인하는 것이 중요하다.
* 통계 기법마다 검정하는 대상이 다르기 때문에 단순히 결과의 p-value가 같다는 이유로 같은 의미의 검정이라고 볼 수 없다는 점을 배웠다. Welch t-test와 Mann-Whitney U의 역할을 구분해서 설명해야 한다.
* 결측값을 단순히 제거하는 것도 하나의 처리 방법이지만, 결측이 특정 그룹에 집중되어 있다면 데이터 분포 자체가 바뀔 수 있다. 따라서 결측 처리 방법뿐 아니라 **처리 전후 데이터의 특성이 유지되는지 확인하는 과정**도 중요하다.
* 머신러닝에서는 Accuracy 하나만으로 모델을 평가하면 클래스 불균형의 영향을 놓칠 수 있다. 이번 데이터처럼 `<=50K`와 `>50K`의 비율이 다른 경우 F1, Precision, Recall 등을 함께 확인해야 모델의 실제 분류 성능을 이해할 수 있다.
* 분석 코드뿐 아니라 재현성과 유지보수성을 고려한 프로젝트 구조도 중요하다는 점을 배웠다. 설정 분리, 함수 및 모듈 분리, 모델 저장/재로딩 검증, 자동 보고서 생성 등이 분석의 신뢰성을 높이는 데 도움이 되었다.

## 개선 의견 (시간이 더 있다면)

* 가장 먼저 소득 그룹별 **40시간 초과 근로 비율**을 직접 계산하여 "고소득 그룹에서 장시간 근로자가 상대적으로 많이 나타난다"는 현재 해석을 정량적으로 검증하고 싶다.
* 현재 결측 보유 행을 제거하는 방식을 사용했으므로, 정제 전후의 `income` 비율, `hours-per-week` 평균·중앙값, 주요 범주형 변수 분포를 비교하여 결측 행 제거가 분석 데이터의 특성에 영향을 주었는지 확인하고 싶다.
* 머신러닝 모델의 경우 현재 단일 train/test split 결과만 비교하고 있으므로, `StratifiedKFold` 교차검증을 적용하여 Logistic Regression과 Random Forest의 평균 F1과 표준편차를 비교하면 모델 성능을 더 안정적으로 평가할 수 있을 것이다.
* Logistic Regression의 계수나 permutation importance 등을 추가하여 어떤 변수들이 소득 예측에 실제로 기여하는지 확인하면 통계 분석과 머신러닝 분석을 보다 자연스럽게 연결할 수 있을 것이다.
* 코드의 일부 docstring이나 주석에 특정 실행 결과값을 직접 기록하면 분석 조건 변경 후 실제 결과와 불일치할 수 있으므로, 주석에는 분석 방법의 선택 이유와 설계 의도를 중심으로 남기고 실행 결과 수치는 자동 생성 보고서에서만 관리하도록 개선하고 싶다.
* 최종적으로는 통계적 유의성, 효과크기, 분포 차이, 머신러닝 예측력을 각각 구분하면서도 하나의 분석 스토리로 연결할 수 있도록 보고서 표현을 더 정교하게 다듬고 싶다.
